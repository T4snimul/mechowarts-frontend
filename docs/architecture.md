# Architecture

## Overview

The application follows a feature-based architecture.

The App Router is responsible only for routing.

Business logic belongs inside features.

Reusable UI belongs inside components.

Utilities belong inside lib.

---

# Folder Structure

app/
components/
features/
hooks/
lib/
services/
stores/
types/

---

## app/

Contains Next.js routing and framework entry files.

Examples:

- page.tsx
- layout.tsx
- loading.tsx
- error.tsx
- not-found.tsx
- route.ts
- favicon.ico
- globals.css
- robots.ts
- sitemap.ts
- manifest.ts

Business logic does not belong here.

Pages should compose feature components rather than implement business logic directly.

---

## components/

Contains reusable UI shared across the application.

Components in this folder must be generic and reusable.
They must not contain feature-specific business logic.

Folder structure:

components/

    ui/            # shadcn/ui components

    shared/        # reusable application components

    layout/        # layouts and navigation

    providers/     # React providers

    icons/         # custom SVG and icon components

---

### ui/

Contains components generated by shadcn/ui.

Examples:

- Button
- Card
- Input
- Dialog
- Table

These components are the foundation of the design system.

Do not place application-specific logic here.

---

### shared/

Reusable components used by multiple features.

Examples:

- Logo
- SearchBar
- UserAvatar
- EmptyState
- LoadingSpinner
- PageHeader

Shared components may compose shadcn components.

---

### layout/

Application layout components.

Examples:

- Navbar
- Sidebar
- Footer
- DashboardLayout
- AuthLayout

---

### providers/

Application-wide React providers.

Examples:

- ThemeProvider
- QueryProvider
- TooltipProvider

Providers are registered from the root layout.

---

### icons/

Custom SVG icons and icon wrappers.

Do not duplicate icons that already exist in lucide-react.

---

### Rules

- Components should have a single responsibility.
- Reuse existing components before creating new ones.
- Keep components presentation-focused.
- Business logic belongs in features or services.
- Components may use hooks but must not perform API requests directly.

---

### Not Allowed

The following do NOT belong here:

- LoginForm
- RegisterForm
- ProfileCard
- ProjectCard
- ChatWindow

Feature-specific components belong inside their respective feature folders.

---

## features/

Features contain business logic and everything related to a specific domain of the application.

Each feature is self-contained and owns its own components, hooks, services, types, and validation schemas.

Example structure:

features/

    auth/
        components/
        hooks/
        services/
        schemas/
        types/
        utils/

    profile/
        ...

    chat/
        ...

    projects/
        ...

---

### Responsibilities

A feature may contain:

- UI specific to that feature
- Business logic
- Custom hooks
- Validation schemas
- Types
- API service wrappers
- Utility functions used only within the feature

---

### Rules

- Keep features independent whenever possible.
- Import reusable UI from `components/`.
- Do not import code from one feature into another unless absolutely necessary.
- Shared logic should be extracted into `lib/`, `components/`, or `hooks/`.
- Pages should compose feature components instead of implementing feature logic directly.

---

### Examples

Correct:

features/auth/components/LoginForm.tsx

features/profile/components/ProfileCard.tsx

features/chat/components/ChatWindow.tsx

Incorrect:

components/LoginForm.tsx

components/ProfileCard.tsx

components/ChatWindow.tsx
---

## lib/

The `lib` directory contains application-wide utilities that are not tied to any specific feature.

Everything inside `lib` should be reusable across the entire application.

Example structure:

lib/

    api/
    auth/
    constants/
    utils/
    validations/

---

### api/

Shared API utilities.

Examples:

- apiClient
- axios instance
- fetch wrapper
- request helpers

This is infrastructure, not business logic.

---

### auth/

Authentication utilities shared across the application.

Examples:

- session helpers
- auth configuration
- permission helpers

---

### constants/

Application-wide constants.

Examples:

- routes
- roles
- navigation
- regex
- configuration values

Avoid magic strings throughout the project.

---

### utils/

Generic helper functions.

Examples:

- formatDate()
- formatCurrency()
- cn()
- debounce()
- slugify()

Utility functions should be pure whenever possible.

---

### validations/

Validation schemas shared by multiple features.

Feature-specific schemas should remain inside their respective feature.

---

### Rules

- Code in `lib` must not depend on a specific feature.
- Prefer pure functions.
- Keep utilities small and focused.
- Business logic does not belong in `lib`.
- If a utility is only used by one feature, keep it inside that feature.

---

## services/

The `services` directory contains application-wide service implementations.

A service is responsible for communicating with external systems such as APIs, databases, storage providers, or third-party services.

Business rules belong in features.
Infrastructure belongs in services.

Example structure:

services/

    api/
        auth.service.ts
        users.service.ts
        projects.service.ts

    storage/
        upload.service.ts

    email/
        email.service.ts

---

### Responsibilities

Services may:

- make HTTP requests
- upload files
- communicate with third-party APIs
- encapsulate infrastructure concerns

Services should not:

- render UI
- contain React code
- contain page logic

---

### Rules

- Components never call fetch() directly.
- Components never call axios directly.
- Features communicate with services.
- Services should return typed data.
- Keep services stateless whenever possible.

---

## hooks/

Reusable hooks shared across multiple features.

---

## stores/

Global Zustand stores.

Do not store server state here.

---

## types/

Global TypeScript types.

---

Application configuration.

Example:

navigation

roles

permissions

environment

Routing → Features → Services → Backend

Never skip layers.

# Application Modules

The application is organized into independent modules.

Each module owns its own business logic.

Initial modules:

- Authentication
- User Profile
- Projects
- Skills
- Experience
- Education
- Blog
- Contact
- Chat
- Admin

New modules should be added as independent features.
